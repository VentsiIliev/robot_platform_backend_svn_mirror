# Настройка на MikroTik mAP и WireGuard VPN

Ръководство за техника, който подготвя машината, и администратора на
фирмения VPN шлюз. Основа:
[предоставеното подробно ръководство във Word](assets/mikrotik-map-wireguard-bg.docx).
Оригиналът съдържа илюстрации и описва конкретна подготовка; настоящите
стъпки са шаблон за нова инсталация, а не потвърждение за нейното състояние.

## Схема и необходими данни

```text
Клиентски интернет → ether1 (WAN) на mAP
                              ├─ Wi-Fi → машинен PC
                              └─ WireGuard → фирмен VPN шлюз → сервизен инженер
```

mAP започва тунела към фирмения шлюз. Инженерът започва сервизната
връзка към PC. Интернетът остава през клиентския WAN; през VPN минават
само одобрените маршрути. Не добавяйте `ether1` към машинния bridge.

Примерът е за **RBmAP2nD**, RouterOS 7 и стария интерфейс `wlan1` с
пакета `wireless`. За друго устройство проверете имената и Wi-Fi пакета.
Предоставеният документ посочва RouterOS 7.20.8 като версия на описаната
подготовка; това не е задължителна версия за всяка бъдеща инсталация.
Изберете поддържана версия, съвместима с устройството и одобрена от администратора.
[Хардуерна спецификация на mAP](https://mikrotik.com/product/RBmAP2nD).

Попълнете таблицата преди настройването. Главните имена са полета за
замяна, не готови адреси или RouterOS променливи.

| Поле | Какво предоставя администраторът |
| --- | --- |
| `MACHINE_ID` | Уникален идентификатор на машината |
| `MACHINE_LAN_CIDR` | Уникална машинна подмрежа, без припокриване с клиентския WAN, фирмата и други машини |
| `ROUTER_LAN_IP` | Адрес на mAP в тази подмрежа |
| `MACHINE_PC_IP` | Запазен адрес на действителния машинен PC |
| `PC_WIFI_MAC` | Постоянният Wi-Fi MAC адрес на този PC |
| `SSID` | Име на Wi-Fi мрежата на машината |
| `VPN_ENDPOINT`, `VPN_PORT` | Публично достижимо име/IP и UDP порт на фирмения шлюз |
| `SERVER_PUBLIC_KEY` | Публичният WireGuard ключ на шлюза |
| `ROUTER_VPN_CIDR` | Уникален тунелен адрес на mAP с маска |
| `SERVER_TUNNEL_IP` | Тунелен IPv4 адрес на шлюза |
| `SUPPORT_CIDR` | Разрешени адреси на сервизните инженери |
| `UPDATE_IP`, `UPDATE_HOSTNAME`, `UPDATE_PORT` | Одобрен сървър за обновявания, име за TLS и порт; проектният вариант е HTTPS/443 |
| `SERVICE_PORTS` | Разрешени сервизни портове, например TCP 22 за SSH |
| `ADMIN_SOURCE_IP` | Отделен разрешен адрес за управление на рутера, ако е необходимо |

Wi-Fi и администраторската парола трябва да са различни. Въвеждат се
локално и не се записват в ръководството. Частният WireGuard ключ
остава на рутера; към администратора се предава само публичният ключ.

## 1. Свържете рутера и отворете управлението

1. Захранете устройството според спецификацията му.
2. Свържете клиентския интернет към **ether1**.
3. Свържете лаптопа за настройка към **ether2**. Оставете този достъп
   наличен, докато всички проверки и аварийният достъп са готови.
4. На лаптопа изберете Ethernet IPv4 **Automatic (DHCP)**.
5. Отворете текущия LAN адрес на рутера. При описаната начална
   конфигурация това е `http://192.168.88.1`; проверете адреса на вашия рутер.
6. Влезте с предоставените данни и задайте уникална администраторска парола.

Преди промени запазете резервно копие от **Files / Backup** в защитено
хранилище. Архивите могат да съдържат чувствителни данни. Не ги добавяйте
в Git. Използвайте Safe Mode при промени, които могат да прекъснат управлението.

Следващите RouterOS команди се изпълняват в **терминала на MikroTik**,
а не в Ubuntu. Проверете текущата конфигурация:

```routeros
/system resource print
/system package print
/interface bridge port print
/ip dhcp-client print
/ip address print
/ip dhcp-server print
/ip firewall filter print
/ip firewall nat print
```

Проверете дали `ether1` е WAN с DHCP клиент, а `ether2` и `wlan1` са
в машинния bridge. Ако началната конфигурация е различна, подгответе
WAN/LAN и DHCP според избраната адресация, преди да продължите.
Не добавяйте повторно вече съществуващи интерфейси или DHCP услуги.

## 2. Проверете WAN и подгответе машинната подмрежа

В **IP → DHCP Client** потвърдете, че WAN клиентът на `ether1` е `bound`.
Проверете интернет и DNS от рутера:

```routeros
/ping 1.1.1.1 count=3
:put [:resolve "example.com"]
```

В **IP → Addresses** задайте `ROUTER_LAN_IP` с маската на избрания
`MACHINE_LAN_CIDR` върху LAN bridge. В **IP → Pool** и
**IP → DHCP Server → Networks** съгласувайте диапазона, подмрежата,
gateway и DNS. При промяна от `192.168.88.0/24` текущата сесия може
да прекъсне; свържете се отново към новия адрес.

Избирайте свободни адреси. Един и същ машинен LAN не трябва да се
използва за множество машини в тази маршрутизирана VPN схема.

## 3. Настройте Wi-Fi за машината

В **Wireless → Security Profiles** създайте или редактирайте `machine-wifi`:

| Поле | Стойност |
| --- | --- |
| Mode | dynamic keys |
| Authentication Types | само WPA2 PSK |
| Unicast / Group Ciphers | само aes ccm |
| WPA2 Pre-Shared Key | уникална силна парола за машината |
| WPA Pre-Shared Key | празно |

В **Wireless → Interfaces → wlan1** задайте:

- Mode: `ap-bridge`; SSID: избраното `SSID`.
- Security Profile: `machine-wifi`.
- Band: `2ghz-b/g/n`; Channel Width: `20mhz`; Frequency: `auto`.
- Country и Installation: действителната държава и място на експлоатация.
- WPS: disabled; интерфейсът: enabled.

Настройките са за legacy `wireless`, а не за менюто `wifi` на други модели.
[Официална документация за Wireless](https://manual.mikrotik.com/docs/wireless/abgn/wireless-interface/).

Свържете действителния машинен PC според [инструкциите за Ubuntu Wi-Fi](network.md).
Включете автоматично свързване и IPv4 DHCP. Проверете адрес, gateway,
интернет и покритие при затворен корпус. Успешната връзка на лаптопа
за настройка не е достатъчна за приемане на машинния PC.

## 4. Запазете IP и ограничете Wi-Fi клиентите

1. На машинния PC изключете случайното/сменящо се Wi-Fi MAC за този профил.
2. В **IP → DHCP Server → Leases** намерете действителния `PC_WIFI_MAC`.
3. Изберете **Make Static** и задайте свободния `MACHINE_PC_IP` от машинния LAN.
4. В **Wireless → Access List** добавете PC MAC за `wlan1` с Authentication=yes
   и Forwarding=no. Проверете и премахнете ненужните разрешаващи правила.
5. На `wlan1` изключете Default Authentication и Default Forwarding.
6. Потвърдете, че PC се свързва, а друг Wi-Fi клиент се отказва.

Работете през `ether2` при тази промяна. MAC ограничението не замества
Wi-Fi паролата: MAC адрес може да се подправи. DHCP резервацията
осигурява постоянен адрес, а не удостоверяване на устройството.

## 5. Създайте WireGuard интерфейс и обменете публичния ключ

Първо проверете дали `wg-company` вече съществува. Създайте го само веднъж:

```routeros
/interface wireguard add name=wg-company mtu=1420
:put [/interface wireguard get [find name="wg-company"] public-key]
```

Предайте показания публичен ключ на фирмения VPN администратор.
Не използвайте чужд лаптопски профил или един ключ за няколко машини.
Интерфейсът генерира ключове автоматично.
[WireGuard в RouterOS](https://manual.mikrotik.com/docs/virtual-private-networks/wireguard/).

## 6. Настройте peer и маршрути на mAP

Заменете всички главни полета с реалните данни. Добавяйте само липсващи
адреси, peers и маршрути; при повторна настройка редактирайте съществуващите.

```routeros
/ip address add address=ROUTER_VPN_CIDR interface=wg-company
/interface wireguard peers add interface=wg-company public-key="SERVER_PUBLIC_KEY" endpoint-address=VPN_ENDPOINT endpoint-port=VPN_PORT allowed-address=SERVER_TUNNEL_IP/32,SUPPORT_CIDR,UPDATE_IP/32 persistent-keepalive=25
/ip route add dst-address=SUPPORT_CIDR gateway=wg-company
/ip route add dst-address=UPDATE_IP/32 gateway=wg-company
```

Ако няма сървър за обновявания през VPN, пропуснете `UPDATE_IP/32` и
неговия маршрут до предоставяне на адрес. Не задавайте `0.0.0.0/0`,
не пренасочвайте default route към тунела и не добавяйте `wg-company`
в доверения LAN interface list. Allowed addresses включват адресите,
които действително трябва да се получават/изпращат през този peer.
Маршрутите и firewall правилата се настройват отделно.

`persistent-keepalive=25` поддържа NAT mapping при изходящ тунел.
Клиентски port forwarding обичайно не е необходим. Фирменият шлюз
трябва да е достижим на зададения UDP порт.

## 7. Настройте фирмения VPN шлюз

Тази стъпка се изпълнява от администратора на шлюза:

1. Създайте отделен peer за машината с публичния ключ на mAP.
2. В неговите AllowedIPs разрешете точния тунелен IP на mAP с `/32`
   и `MACHINE_LAN_CIDR`. Не добавяйте фирмените адреси като машинни източници.
3. Осигурете маршрут към машинния LAN през този peer и обратните маршрути
   от сервизната мрежа. При Linux проверете IP forwarding.
4. Разрешете входящия WireGuard UDP порт на шлюза.
5. Настройте централния firewall според таблицата по-долу. Изолирайте
   машинните peers един от друг и от служителския VPN.

| Трафик | Действие |
| --- | --- |
| Одобрени инженери → конкретния PC, одобрени портове | разрешаване |
| Отговори по разрешени установени сесии | разрешаване |
| PC → одобрения update сървър/порт | разрешаване само при необходимост |
| Машина → друга машина или други фирмени услуги | забрана |
| Машина → услуги на самия шлюз | забрана, освен конкретни изключения |

Правилата трябва да се приложат преди широките accept правила и
FastTrack. AllowedIPs не замества firewall политиката. Точните команди
зависят от платформата на фирмения шлюз и съществуващата конфигурация.

## 8. Ограничете VPN трафика на mAP

В **IP → Firewall → Filter Rules** прегледайте текущия ред. Добавете
отделни правила с ясни коментари и ги поставете преди широките
разрешения и FastTrack. Последователността за VPN във `forward` е:

1. Отхвърляне на invalid трафик.
2. Разрешаване на established отговори за одобрените VPN сесии.
3. Разрешаване на new от `wg-company`, `SUPPORT_CIDR` към
   `MACHINE_PC_IP` само на `SERVICE_PORTS`.
4. Разрешаване на new от `MACHINE_PC_IP` към `UPDATE_IP`, TCP,
   `UPDATE_PORT`, през `wg-company`, ако този достъп се използва.
5. Отхвърляне на останалия трафик с in-interface или out-interface `wg-company`.

Запазете WAN правилата и интернет NAT. В маршрутизираната схема не
маскирайте PC трафика към VPN; проверете дали широк masquerade не го обхваща.

В `input` разрешете необходимите LAN услуги и установени отговори.
Управление през VPN се разрешава само от `ADMIN_SOURCE_IP` към
конкретна услуга преди VPN drop. Ако mAP обслужва DNS, TCP/UDP 53
трябва да е достъпен само от одобрения LAN. Не отваряйте управление
или DNS към клиентския WAN. При нужда ограничете и router-originated
достъпа до фирмата в `output`. За IPv6 приложете еквивалентна политика
или не предоставяйте IPv6 достъп през машинния VPN.

Ограничете SSH/WebFig/WinBox до административните адреси и прегледайте
MAC WinBox, MAC server, neighbor discovery, RoMON и неизползваните
интерфейси. Не изключвайте единствения работещ начин за управление.
[Официален RouterOS firewall filter](https://help.mikrotik.com/docs/spaces/ROS/pages/48660574/Filter).

## 9. Съгласувайте достъпа до софтуерните обновявания

Сървърът в `updates.json` трябва да е достижим по разрешения маршрут,
порт и име. Проектният вариант е HTTPS/443. Текущият Gitea тестов
адрес използва HTTP/3000 и няма да работи през правило само за 443.
За внедряване подгответе одобрения HTTPS адрес или изрично различна политика.

IP firewall ограничава IP и порт, не URL или права в Gitea. Ограничете
машинния достъп до четене на сървъра и използвайте правилен TLS сертификат.
Redirect към друг сървър изисква отделен разрешен достъп. Ако е нужен
вътрешен DNS, одобрете точния DNS адрес и действителния заявител.

Първоначалната софтуерна подготовка използва и Ubuntu хранилища и
GitHub за дистанционната поддръжка. Един разрешен update IP не покрива
тези зависимости. Съгласувайте WAN достъпа за първа инсталация и
бъдещите обновявания на поддръжката. Тази политика за фирмения VPN
сама по себе си не ограничава всички PC връзки към публичния интернет.

Продължете с [инсталация](software.md) и [обновяване](updates.md) след
потвърден достъп до съответните източници.

## 10. Проверете преди предаване

```routeros
/interface wireguard peers print
/interface wireless registration-table print
/ip dhcp-server lease print
/system resource print
```

Проверете handshake, адресите, броячите за трафик, маршрути и услугата
на PC. Handshake доказва тунел, но не доказва достъп до приложението.

| Тест | Очакван резултат |
| --- | --- |
| Рестарт на PC и рутера | Wi-Fi, WAN DHCP и тунелът се възстановяват |
| Одобрен инженер към разрешен PC порт | успешна реална сервизна сесия |
| Неодобрен източник или друг PC порт | отказ |
| PC към друг фирмен IP или друга машина | отказ |
| PC към одобрения update сървър | успешно изтегляне на реален пакет |
| Друг Wi-Fi клиент | не се свързва |
| Отпадане и връщане на интернет | тунелът се възстановява |

При тестовете за забрана използвайте реален IP и слушаща услуга;
затворен порт или неработещ DNS не доказва firewall защита. Проверете
броячите на правилата и повторете тестовете след рестарт. Приемните
проверки на реален рутер още не са извършени с това ръководство.

## 11. Финализирайте и запазете аварийния достъп

След успешни тестове запазете конфигурацията и документирайте
разрешения административен/авариен достъп. Ако ether2 няма да се
използва при клиента, изключете го само когато имате друг проверен
начин за управление:

```routeros
/interface ethernet disable ether2
```

Възстановяване от разрешена сесия:

```routeros
/interface ethernet enable ether2
```

Изключете PoE-out и други неизползвани локални входове според
реалното оборудване. Запишете идентификатор, сериен номер, RouterOS
версия, SSID, PC MAC/IP, LAN, VPN IP, публичен ключ и разрешени портове.
Съхранявайте паролите, частните ключове и чувствителните архиви отделно.

За клиента: включете машината, свържете интернет към **INTERNET / WAN**
и изчакайте връзката. Клиентска мрежа с captive portal, VLAN, PPPoE,
802.1X или блокиран UDP изисква съдействие от местния IT администратор.
